### MSIX discovery correction

Microsoft documents that packaged apps opening AppData files first read an existing per-user/per-package private copy. An absolute path alone therefore cannot bypass a stale shadow `runtime.json`. The original packaging error could leave exactly that file after launching the GUI under the MCP client's package identity. Treating its dead PID as stale improves diagnostics but cannot discover the real desktop behind it. The release must use one Windows runtime-descriptor location outside AppData, scoped by the configured workspace, and must not fall back to the old shadow file. This changes only endpoint discovery, not database or asset storage. Reference: [Microsoft MSIX file virtualization](https://learn.microsoft.com/en-us/windows/msix/desktop/desktop-to-uwp-behind-the-scenes).

## Candidate and scope

Issue [#68](https://github.com/glanderness/BeefTV/issues/68) reports that the canvas assistant cannot resolve a custom local channel despite an enabled channel, stored key, OpenAI format, a models list and a default text selection. The resolver required a matching model profile, while this persisted configuration had none.

Current source candidate `0ddc37f2e487e76e3392774b1c13d78bce659321`, based on `36c9f67`, combines the assistant fix and updater cleanup. Its source digest is `afcbb52d0e08b80ebc4bfd5872bdc63bfe68d0f33274779f61c4432349a210ec`. The assistant implementation was first verified at `b31d35f72c1e0c94a7fe82f9ea309cccee59906b` and is unchanged in this candidate. A profile-free custom model is accepted only when it is the selected default text model and its channel protocol is supported. Explicit capabilities, disabled channels, managed-channel restrictions and credential checks remain in force.

The second report showed `.beeftv-update-*` directories accumulating beside the application. The helper retained its backup after spawning the new process, with no successful-startup confirmation to remove it. Cleanup now requires the rendered desktop, successful asset/canvas cache hydration and successful canonical workspace, canvas-list and asset-list reads. It accepts only completed records for the same install and exact updater-owned sibling layout. Failed, rolled-back, incomplete, unknown-content and active updates retain their recovery files; overlapping user data is excluded.

Windows uses an exclusive delete-on-close lock. macOS retains its zero-byte lock: unlinking its inode would allow a pending old-version helper and a new helper to acquire different locks. This file is not an upgrade archive or application backup.
